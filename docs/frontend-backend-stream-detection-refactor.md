# 前后端推拉流与检测链路改造清单

## 1. 目标

把当前“后端既做检测又做预览推流/转码编排”的模式，调整为：

- 前端负责视频播放、电子围栏绘制、检测框叠加
- 后端负责拉流解码、检测、报警图、报警视频、事件落库
- 流媒体层负责把摄像头/WVP 流转成浏览器可播放协议
- 后端不再承担前端预览播放控制、区域预览推流、浏览器预览编排

这次改造的核心原则有三个：

- 检测链路和预览链路解耦
- 保留按任务拉流；同一任务只对应一个通道
- 报警图、报警视频从“检测帧/缓存片段”生成，不依赖预览流

---

## 2. 前端改造清单

### 2.1 播放链路

- [ ] 前端播放器改为直接消费浏览器可播地址：`webrtc` / `hls` / `http-flv`
- [ ] 去掉“开始播放后由后端推一个预览流再播放”的依赖
- [ ] 播放器只关心播放地址，不关心后端是否建立了额外预览代理
- [ ] 播放失败时，前端只提示“地址无效/流不可达/协议不可播”，不再触发额外预览链路

### 2.2 电子围栏交互

- [ ] 所有电子围栏绘制都放到前端 `canvas`
- [ ] 围栏坐标保存为归一化坐标，而不是像素坐标
- [ ] 前端保存围栏时，统一传：
  - `channel_id`
  - `algorithm_id` 或任务关联标识
  - `normalized_points`
  - `name`
  - `enabled`
- [ ] 围栏更新只更新坐标和绑定关系，不再触发区域预览转码

### 2.3 实时检测框叠加

- [ ] 通过 `websocket` 接收后端检测结果
- [ ] 前端按检测结果在 `canvas` 上画：
  - 框
  - 类别
  - 置信度
  - 所属围栏（可选）
- [ ] 叠加绘制与视频播放解耦，播放中断不影响围栏编辑和结果展示逻辑

### 2.4 页面与交互收口

- [ ] 通道管理页保留：
  - 通道基础信息
  - 播放地址展示
  - 在线状态
  - 围栏编辑入口
- [ ] 任务页保留：
  - 通道绑定
  - 算法配置
  - 围栏绑定
  - 报警参数
- [ ] 下线或隐藏以下前端能力：
  - 区域预览流
  - 浏览器预览转码状态
  - task preview 相关操作
  - zone preview 相关操作

---

## 3. 后端改造清单

### 3.1 任务采集与检测架构

- [ ] 保留“按任务拉流”
- [ ] 一个任务只对应一个通道
- [ ] 同一任务内多个算法共享同一份解码帧
- [ ] 一个任务只保留一个采集器/解码器实例
- [ ] 不同任务即使绑定同一通道，也允许各自独立拉流，便于任务隔离和独立启停
- [ ] 检测主循环只负责：
  - 拉流
  - 解码
  - 推理
  - 围栏过滤
  - 报警判定

### 3.2 检测与围栏逻辑

- [ ] 后端只接收归一化围栏坐标
- [ ] 检测时按当前帧分辨率还原围栏坐标
- [ ] 围栏过滤逻辑独立成统一模块，供所有 detection 类算法复用
- [ ] 不再生成“围栏专用预览流”

### 3.3 预览播放相关后端能力收缩

- [ ] 后端不再负责前端的“开始播放/停止播放”主流程
- [ ] 保留“获取播放地址”接口，但职责只剩返回浏览器可播放地址
- [ ] 删除或弱化以下运行态：
  - `browser_transcode`
  - `task_preview`
  - `zone_preview`
  - 与区域预览强绑定的推流状态

### 3.4 报警图生成

- [ ] 报警图直接基于触发时的检测帧生成
- [ ] 保存前在帧上绘制：
  - 检测框
  - 类别
  - 置信度
  - 触发时间
  - 算法名/围栏名（可选）
- [ ] 报警图生成不依赖预览流，不依赖前端绘制结果

### 3.5 报警视频生成

- [ ] 不直接缓存大量 OpenCV 原始帧
- [ ] 改为通道级环形缓存
- [ ] 优先缓存短视频片段或编码后数据，不优先缓存完整 BGR 帧
- [ ] 报警触发时：
  - 取前 10 秒缓存
  - 继续收后 10 秒
  - 异步生成 20 秒报警视频
- [ ] 报警视频生成使用后台 worker，不阻塞检测主循环

### 3.6 事件处理与异步任务

- [ ] 报警事件先创建事件记录
- [ ] `video_path` 初始为空
- [ ] 视频生成队列异步处理完成后回填 `video_path`
- [ ] 若视频生成失败，事件状态标记为 `video_failed`
- [ ] 若成功，标记为 `video_ready`

## 4. 数据表调整清单

### 4.1 channels / tasks / task_algorithms

- [ ] `channels` 保留通道基本信息、播放地址、在线状态
- [ ] `tasks` 明确保留任务与通道绑定关系
- [ ] `task_algorithms` 保留算法配置、报警间隔、模型绑定、是否启用

### 4.2 围栏数据

- [ ] 围栏坐标统一存为归一化坐标
- [ ] 推荐字段：
  - `channel_id`
  - `task_id`
  - `algorithm_id`
  - `name`
  - `coordinates_json`
  - `enabled`
- [ ] 若已有表存的是像素坐标，需要增加一次坐标迁移或兼容转换

### 4.3 通道运行态

- [ ] 增加或统一以下运行态字段：
  - 拉流状态
  - 解码状态
  - 检测状态
  - 最近取帧时间
  - 最近检测时间
  - 最近报警时间
- [ ] 运行态尽量作为 runtime 字段或独立 runtime 结构保存，不混入业务配置

### 4.4 事件与报警视频状态

- [ ] `events` 表建议补充或统一以下字段：
  - `snapshot_path`
  - `video_path`
  - `video_status`
  - `task_id`
  - `algorithm_id`
  - `channel_id`
  - `remark`
- [ ] `video_status` 建议值：
  - `pending`
  - `generating`
  - `ready`
  - `failed`

### 4.5 历史逻辑兼容字段

- [ ] 梳理并逐步淘汰以下历史字段：
  - `zone_preview`
  - `task_preview`
  - `browser_transcode`
  - 与区域流、围栏预览相关的临时字段

## 5. 分阶段实施计划

### Phase 1：前端围栏前置

目标：不动检测主干，先把围栏交互迁到前端。

- [ ] 前端接管围栏绘制
- [ ] 围栏坐标改为归一化存储
- [ ] 后端围栏接口只收坐标和绑定关系
- [ ] 保留现有检测链路

交付结果：

- 前端可独立完成围栏编辑
- 后端不再参与围栏预览生成

### Phase 2：任务级共享检测链路

目标：保留任务级隔离，同时避免同一任务内多个算法重复拉流。

- [ ] 按任务创建采集器/解码器
- [ ] 每个任务只绑定一个通道
- [ ] 同一任务内多算法共享一份帧流
- [ ] 任务之间保持独立启停和独立异常恢复
- [ ] 检测主循环输出统一结果事件

交付结果：

- 同一任务内算法并行判断，但不重复拉流
- 任务隔离更清晰，单个任务异常不影响其他任务

### Phase 3：去掉区域预览/浏览器转码耦合

目标：彻底把预览从后端业务编排里拆出去。

- [ ] 下线区域预览流相关接口
- [ ] 下线 task preview / zone preview 相关运行态
- [ ] 前端只通过播放地址直接播放
- [ ] 后端只保留播放地址查询能力

交付结果：

- 预览链路简化
- 后端从“预览编排”退回到“检测服务”

### Phase 4：报警图与报警视频重构

目标：报警媒体输出完全独立于预览流。

- [ ] 报警图改为检测帧直接绘制保存
- [ ] 建立通道级环形缓存
- [ ] 实现前 10 秒 + 后 10 秒视频生成
- [ ] 视频生成异步化

交付结果：

- 报警图稳定
- 报警视频时长稳定
- 生成视频不阻塞检测

### Phase 5：历史逻辑清理与收口

目标：移除旧链路，降低维护成本。

- [ ] 清理旧接口
- [ ] 清理旧 runtime 字段
- [ ] 清理旧前端 UI
- [ ] 更新文档与接口说明

交付结果：

- 系统职责边界清晰
- 运行逻辑统一
- 后续扩展成本降低

## 6. 风险点与建议

### 6.1 最大风险点

- 浏览器不能直接拉 RTSP，必须保留流媒体协议转换层
- 如果直接缓存 OpenCV 原始帧，内存会快速暴涨
- 如果同一任务内每个算法各自拉流，资源问题仍然不会根治
- 如果围栏坐标不归一化，前后端分辨率不一致时会错位
- 如果报警视频生成同步执行，会拖慢检测主循环

### 6.2 建议的实现策略

- 先做“前端围栏前置”和“任务级共享检测”
- 再做“区域预览链路下线”
- 最后做“报警视频环形缓存异步生成”

### 6.3 推荐保留的底层能力

- 保留 WVP / ZLM 作为流接入和浏览器播放协议转换层
- 保留后端统一的检测与事件生成能力
- 保留后端对报警图和报警视频的完全控制

---

## 7. 建议的最终形态

最终建议落成下面这套架构：

- 前端：
  - 直接播放浏览器可播流
  - 画围栏
  - 画实时检测框
- 后端：
  - 任务级采集
  - 同一任务内多算法共享检测
  - 报警图保存
  - 报警视频异步生成
- 流媒体层：
  - 仅负责协议转换和播放入口
- 数据层：
  - DB 主导配置、任务、围栏、事件

这套架构比当前模式更适合你现在的场景：多任务、多围栏、GPU 检测、事件视频、前端直接预览。
