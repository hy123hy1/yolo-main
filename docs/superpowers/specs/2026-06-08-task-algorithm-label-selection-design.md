# 任务算法类别选择优化设计

## 背景

当前任务算法配置弹窗中，类别使用一个自由输入框：

- 用户需要自己输入 `person,truck` 这类标签
- 留空默认表示“全部类别”
- 对于 `yolov8n.pt` 这类通用模型，留空等于把 80 个类别全部打开

这会带来几个问题：

- 普通用户并不知道该选什么类别
- 用户很容易无意中开启全部类别
- 告警噪音、误报、抓拍、录像都会明显增加
- “算法是做什么的”与“模型有哪些类别”之间没有产品化引导

目标不是单纯减少前向推理算力，而是降低噪音、提升配置成功率、让客户更容易理解算法配置。

## 设计目标

1. 通用模型不再默认“全部类别”
2. 用户优先从“检测目标”角度配置，而不是直接面对类别字符串
3. 系统可以提供推荐，但不能擅自替用户选中
4. 保留高级用户的自定义能力
5. 后端语义清晰，不再让 `labels=[]` 隐式表示“全部类别”

## 方案对比

### 方案 A：极简按钮版

- 在类别输入框上方增加几个快捷按钮：`人员`、`货车`、`车辆`、`全部类别`、`自定义`
- 点击后直接改写 `labels`

优点：

- 改动最小
- 能快速缓解“用户不知道怎么填”

缺点：

- 仍然保留自由文本输入，结构不够清晰
- “推荐”和“已选中”状态不够直观

### 方案 B：推荐卡片 + 高级自定义版（推荐）

- 模型选中后，系统根据模型类别生成“推荐目标”
- 用户点击推荐卡片后，才真正写入算法配置
- 同时保留“高级自定义”展开面板
- “全部类别”作为显式风险操作

优点：

- 最符合面向客户的产品化体验
- 兼顾新手和高级用户
- 能清晰区分“推荐”与“已选中”

缺点：

- 前端交互比方案 A 稍复杂

### 方案 C：向导式配置版

- 先选“检测目标”
- 再进入算法策略和区域配置

优点：

- 流程最强约束

缺点：

- 路径变长
- 不适合当前任务页的轻量弹窗模式

## 结论

采用 **方案 B：推荐卡片 + 高级自定义版**。

## 前端交互设计

基于当前 [AlgorithmEditorModal.vue](G:\docker\yolo-main\frontend\src\components\channels\AlgorithmEditorModal.vue) 改造。

### 一、弹窗结构调整

当前结构：

- 模型
- 算法类型
- 置信度
- 告警间隔
- 视频时长
- 算法状态
- 类别文本框
- 保存抓拍图 / 保存报警视频 / 需要画框 / 启用算法

调整后结构建议：

1. 基础配置区
   - 模型
   - 算法类型
   - 置信度
   - 告警间隔
   - 报警视频时长（只读 6 秒）
   - 启用算法

2. 检测目标区（核心改造）
   - 标题：`检测目标`
   - 说明：`先选择业务目标，系统会自动匹配对应类别`
   - 推荐卡片区
   - 全部类别风险入口
   - 高级自定义展开区

3. 输出策略区
   - 保存抓拍图
   - 保存报警视频
   - 需要画框

4. 画框提示区
   - 当 `need_overlay=true` 时，展示区域配置说明

### 二、检测目标区详细设计

#### 1. 推荐卡片

模型选中后，根据 `model.classes` 动态生成推荐卡片。

示例卡片：

- `人员检测`
- `货车检测`
- `车辆检测`
- `二轮车检测`
- `全部类别`
- `自定义`

卡片状态：

- `推荐`：系统建议，但未生效
- `已选中`：用户点击后生效

规则：

- 模型切换后，系统重新计算推荐项
- 系统只高亮“推荐”，不自动选中
- 用户点击卡片后，才真正写入 `labels`

#### 2. 推荐映射规则

通用模型建议内置一份业务映射：

- `人员检测` -> `["person"]`
- `货车检测` -> `["truck"]`
- `车辆检测` -> `["car", "bus", "truck", "motorcycle", "bicycle"]`
- `二轮车检测` -> `["motorcycle", "bicycle"]`

生成卡片时，只保留模型里真实存在的类别。

例如：

- 模型有 `person, car, truck, bus`
  - 展示：`人员检测`、`货车检测`、`车辆检测`
- 模型只有 `helmet, person`
  - 展示：`人员检测`
- 模型类别很少且明显是专用模型
  - 可展示：`推荐：全部类别`

#### 3. 全部类别入口

“全部类别”必须是显式操作，不可作为默认状态。

交互：

- 卡片文案：`全部类别`
- 辅助提示：`可能带来较多误报和告警，通常仅用于调试或泛检测`

点击后：

- 清空 `labels`
- 设置 `label_mode = "all"`

#### 4. 高级自定义

点击 `自定义` 或 `高级自定义` 后展开：

- 类别搜索框
- 类别多选列表
- 已选数量
- `全选`
- `取消全选`

交互要求：

- 用户在高级区手动多选后，系统自动切换为 `label_mode = "custom"`
- 若用户把所有已选项清空，不自动回到“全部类别”
- 应提示：`请至少选择一个类别，或显式选择“全部类别”`

### 三、默认规则

#### 通用模型

如 `yolov8n.pt`、`yolov8s.pt`：

- 默认不选任何类别
- 只展示推荐项
- 用户必须点击某个推荐项、或手动自定义、或显式点“全部类别”后，才能保存并应用

#### 专用模型

如果模型类别数较少，例如：

- `["helmet"]`
- `["person", "helmet"]`
- `["smoke", "fire"]`

则可以：

- 默认展示“推荐：全部类别”
- 但仍不自动生效，保持混合型策略一致

## 前端字段设计

当前算法对象关键字段：

- `labels`
- `need_overlay`
- `need_snapshot`
- `need_video_clip`

建议新增两个前端字段语义：

- `label_mode`
  - `recommended`
  - `custom`
  - `all`
- `preset_key`
  - `person`
  - `truck`
  - `vehicle`
  - `two_wheeler`
  - `all`
  - `custom`

说明：

- `preset_key` 用于 UI 展示“当前选的是哪个业务目标”
- `label_mode` 用于决定提交和校验逻辑

## 后端接口语义设计

当前后端通过 `labels=[]` 表示“全部类别”，这个语义不够清晰。

建议改为显式表达：

- `labels`
- `detect_all_classes`

推荐接口语义：

- 自定义类别：
  - `labels=["person","truck"]`
  - `detect_all_classes=false`

- 全部类别：
  - `labels=[]`
  - `detect_all_classes=true`

后端判断规则：

1. `detect_all_classes=true`
   - 不进行类别过滤

2. `detect_all_classes=false` 且 `labels` 非空
   - 仅过滤所选类别

3. `detect_all_classes=false` 且 `labels` 为空
   - 视为非法配置
   - 返回 400：`请至少选择一个类别，或显式启用全部类别`

这样比当前“空数组即全部类别”的隐式规则更稳。

## 任务详情区展示优化

当前 [TaskDetailPanel.vue](G:\docker\yolo-main\frontend\src\components\channels\TaskDetailPanel.vue) 中的：

- `类别数：0 => 全部`

建议改成：

- `检测目标：人员检测`
- `检测目标：货车检测`
- `检测目标：自定义（2类）`
- `检测目标：全部类别`

也就是尽量使用“业务语言”，少用“类别数”。

## 校验规则

保存算法时校验：

1. 未选模型，不允许保存
2. 若 `label_mode=custom`，则 `labels` 至少 1 个
3. 若未选择任何推荐项、也未开启全部类别、也未进入自定义选中类别
   - 不允许保存
4. 若选择“全部类别”
   - 可保存，但需显式风险提示

## 对分析链路的影响

当前分析逻辑在 [analysis_service.py](G:\docker\yolo-main\backend\src\services\analysis_service.py) 中通过 `labels` 做过滤。

改造后：

- 过滤逻辑需要同时读取 `detect_all_classes`
- `detect_all_classes=true` 时跳过 `_filter_detections_by_labels`

区域过滤逻辑不受影响。

## 兼容性策略

为了兼容已有任务：

旧数据迁移建议：

- 若历史算法 `labels` 非空
  - 自动视为 `detect_all_classes=false`

- 若历史算法 `labels` 为空
  - 自动视为 `detect_all_classes=true`

这样旧任务行为不会变化。

## 实施范围

第一阶段：

1. 算法配置弹窗 UI 改造
2. 增加推荐卡片逻辑
3. 增加高级自定义多选
4. 前端提交新增 `detect_all_classes`
5. 后端保存与分析逻辑兼容新语义
6. 任务详情区展示优化

第二阶段：

1. 增加更多业务预设
2. 支持行业模板（如周界、离岗、车辆、烟火）
3. 支持模型级默认推荐模板

## 最终效果

改造后，客户使用流程会变成：

1. 选模型
2. 系统展示推荐目标
3. 用户点“人员检测”或“货车检测”
4. 系统自动填好类别
5. 用户再决定是否画框、是否保存抓拍、是否保存视频
6. 需要时再进入高级自定义

这样客户看到的是“我要检测什么”，而不是“我要填哪些 class 名称”。
